# Правила работы команды Paralax

## Источник истины

- Команда выбрала трек автоматизации заказов поставщикам. Детали продукта в `docs/spec.md` уточняются после выбора стека и проверки данных партнёра.
- Перед изменением кода прочитайте `docs/spec.md`, `docs/tasks.md`, относящиеся к задаче файлы в `contracts/` и `git status`.
- Если реализация требует изменить критерий приёмки или смысл поля, сначала обновите спецификацию и контракт в отдельном небольшом изменении.
- `README.md` даёт обзор кейса; точные критерии MVP находятся в `docs/spec.md`.

## Совместная работа

- `main` служит для интеграции. После подготовительного коммита работайте в личной ветке `feat/<member>/<short-task>` и отдельном клоне или `git worktree`.
- Перед PR выполните `git fetch origin`, затем `git rebase origin/main`. При конфликте сверяйтесь со спецификацией и контрактами; после разрешения запускайте доступную команду `check`.
- Контракты и фикстуры меняет их назначенный владелец либо участник с его согласия. Сначала интегрируйте изменение контракта, затем зависимый код.
- Не мержите в `main` без подтверждения интегратора. Не используйте `git push --force`; `--force-with-lease` допустим лишь по явному указанию в собственной ветке.
- Не присваивайте другому участнику авторство коммита. В `docs/tasks.md` указывайте реального владельца задачи после распределения ролей.

## Данные и качество

- Схема данных → валидация → синтетические фикстуры → расчёт → интерфейс. Не выводите типы из моков.
- Рекомендуемое количество рассчитывается воспроизводимым кодом; LLM может объяснять результат, но не становится источником количества, остатка или срока поставки.
- Для MVP требуется OpenAI-объяснение по проверенным факторам. Вызывайте API только с backend, валидируйте ответ и обеспечьте резервный текст при ошибке. Не отправляйте исходные Excel во внешний API без разрешения партнёра.
- Разовая крупная продажа помечается и объясняется; она не удаляется без правила и проверки. Периоды отсутствия товара не трактуются как нулевой спрос.
- Заказ поставщику не отправляется автоматически. Утверждение выполняет человек. Не добавляйте реальные данные клиентов или API-ключи в Git, фикстуры и отчёты.
- После выбора стека добавьте `check`: lint, typecheck, тесты и сборка. Не объявляйте работу готовой до прогона проверок и демо-сценария.

## Ежечасный результат

- Каждый участник записывает фактический прогресс в `docs/updates/<member>/<HHMM>.md`: сделано, ссылка на коммит/PR, файлы, проверки, демо-артефакт, следующий шаг и блокеры.
- Для следующей сессии оставляйте в `docs/tasks.md` актуальные статусы и владельцев.
