# Этап 6 — рекомендуемый заказ и срочность

Заказ рассчитывается из результата [этапа 5](deficit.md). Это черновая рекомендация для человека, а не отправленный поставщику заказ. Все промежуточные JSONL и карточки SKU сохраняются локально в `.analysis/`; исходные книги Excel не меняются.

## Формула и смысл статусов

- Если `deficit` неизвестен, `purchase_needed`, `recommended_order` и `urgency` равны `null` (`status=unavailable`). Неизвестный остаток или товар в пути не считается нулём.
- Если арифметический дефицит получен только по **неподтверждённому** остатку или товару в пути (`status=provisional` этапа 5), его число остаётся видимым для диагностики, но `purchase_needed`, `recommended_order` и `urgency` равны `null`. Ответ на вопрос о закупке появляется только после ввода/подтверждения текущих величин на дату планирования.
- Если подтверждённый `deficit = 0`, `purchase_needed=false`, `recommended_order=0`; правило поставщика для нулевого заказа не требуется. Срочность определяется отдельно по риску ожидания товара в пути.
- Если `deficit > 0`, `purchase_needed=true`. Для Systeme Electric поле `Кратность` задаёт шаг: `ceil(deficit / multiple) × multiple`. Для IEK поле `Мин. разр. к отгр.` временно трактуется как минимальная разовая отгрузка: `max(ceil(deficit), minimum_dispatch)`. Это **не** кратность, поэтому заказ IEK, полученный по этому толкованию, помечен `provisional` до подтверждения смысла поля у партнёра. Пример общего правила: дефицит 163, кратность 20 → заказ 180.
- При положительном дефиците, но отсутствующем или некорректном правиле, факт потребности известен, а `recommended_order=null` и `status=unavailable`.

Уровень срочности отражает **риск временного отсутствия товара** в выбранном сценарии: `HIGH`, если текущий остаток меньше прогнозируемого спроса за срок поставки; `MEDIUM`, если этого остатка хватает на срок поставки, но он вместе с товаром в пути не покрывает целевой запас со страховым запасом; `LOW`, если новый заказ не нужен **и** текущий остаток покрывает спрос за срок поставки. Товар в пути влияет на количество заказа, но не снижает `HIGH`, поскольку даты его фактического прихода и охват поставок не подтверждены для каждого SKU. Поэтому возможна пара **заказ 0 / риск HIGH**: формула не требует нового заказа, но приход уже едущего товара нужно проконтролировать. Основание класса записывается в `urgency_reasons`.

Расчёт использует целые единицы заказа. Дробный дефицит остаётся видимым в `raw_deficit`; округление происходит только на этапе 6. Погрешность двоичной арифметики меньше `1e-9` единицы у целой границы/границы упаковки не создаёт лишнюю упаковку. Поля результата содержат SHA-256 входных JSONL, тип и величину правила, ссылки на исходные ячейки, качество баланса и причины условного/недоступного результата. Несовпадение файла необходимого запаса с использованным на этапе 5 SHA-256 отклоняется.

## Пользователь вводит текущий остаток

В переданных данных нет надёжного текущего остатка IEK; сводка Systeme не подтверждает единую дату и охват склада. Поэтому `backend/apply_stock_inputs.py` принимает `--stock 'БРЕНД:SKU=КОЛИЧЕСТВО'` с обязательной датой. Если товар в пути неизвестен или его значение нужно подтвердить на эту же дату, пользователь также вводит `--transit`. Вводится только известное число; явный `0` означает подтверждённое отсутствие, а пропуск остаётся `null` либо сохраняет условное значение из источника.

Результат помечает ввод как `basis=user_entered_attested`, `verification=user_attested_not_independently_verified`. При замене значения исходное свидетельство сохраняется рядом в `source_current_stock` или `source_goods_in_transit` локального файла балансов. Метка `calculated` означает воспроизводимый расчёт **по указанным пользователем данным**, а не независимую сверку с 1С или складом. Пользователь отвечает за дату, состав складов и отсутствие двойного учёта товара в пути. Изменение остатка/товара в пути требует повторного запуска этапов 5 и 6.

## Проверка на исходных книгах и учебном вводе

Экстрактор прочитал книги MOQ из неизменяемого коммита `a7a1d3bcd25ab137eac7915f29a4e5c2f5a0f5bc`. Получено **2 491** уникальное правило: IEK — 1 937 минимумов (15 ячеек `#N/A`), Systeme — 554 кратности. Повтор IEK `270400035_` имеет одинаковое значение 6 в обеих строках и сохраняет обе ссылки на ячейки. В книге месячных продаж Systeme встречается вторичный ноль в поле кратности; источником правила служит отдельная MOQ-книга. **82 правила** относятся к SKU, которых нет в результате этапа 5, и не добавляют вымышленные строки заказа.

Без пользовательского ввода по 3 561 SKU получено 469 условных **арифметических дефицитов** на основе неоднозначной сводки Systeme и 3 092 недоступных результата. Для этих 469 строк ответ `purchase_needed` и заказ не выдаются. Для проверки ввода использованы реальные SKU, прогнозы и правила из источника, но следующие остатки и количества в пути — **учебные значения, введённые вручную**, а не измеренный склад:

Для реального решения замените учебные числа актуальными, датированными значениями пользователя. Исторический сентябрьский остаток IEK по-прежнему не считается текущим. При неизвестном товаре в пути не вводите `0` ради получения числового ответа.

## Повторить самостоятельно

Из корня `feat/codex/backend` установите `backend/requirements.txt` и подготовьте этапы 1–5 по [инструкциям необходимого запаса](target-stock.md) и [дефицита](deficit.md). Затем выполните пример PowerShell (все введённые количества ниже учебные):

```powershell
python backend/extract_packing_rules.py
python backend/apply_stock_inputs.py --as-of-date 2026-09-23 `
  --stock 'IEK:081100277_=10' --transit 'IEK:081100277_=0' `
  --stock 'Systeme Electric:300200851_=9' --transit 'Systeme Electric:300200851_=0' `
  --stock 'Systeme Electric:300200720_=3' --transit 'Systeme Electric:300200720_=80'
python backend/deficit.py --balances .analysis/balances/user-input.jsonl `
  --output-dir .analysis/deficit/user-input --sku 081100277_ --sku 300200851_ --sku 300200720_
python backend/order_recommendation.py --deficit .analysis/deficit/user-input/all-skus.jsonl `
  --output-dir .analysis/orders/user-input --sku 081100277_ --sku 300200851_ --sku 300200720_
python -m unittest discover -s backend -p 'test_*.py' -q
```

Откройте `.analysis/orders/user-input/iek-081100277_.html`, `.analysis/orders/user-input/systeme-300200851_.html` и `.analysis/orders/user-input/systeme-300200720_.html`. Рядом находятся JSON и CSV; полный результат — `.analysis/orders/user-input/all-skus.jsonl`. Для другого SKU повторите `--stock`/`--transit`, пересчитайте дефицит и заказ; если не хватает прогноза или правила, результат останется недоступен с причиной.

После этапа 6 работа останавливается. Следующий этап 7 — единая трассировка всей цепочки SKU — выполняется только по новой команде пользователя.
