# Этап 7 — «Как получен результат» для одного SKU

`backend/trace_sku.py` создаёт локальную страницу HTML и точный JSON для любого `(бренд, SKU)` из результатов этапов 1–6. Страница показывает непрерывную цепочку: **исходные строки продаж и документов → корректировки → чистый спрос → взвешенная база → тренд и сезонность → помесячный прогноз → спрос за срок поставки → страховой и необходимый запас → введённый текущий остаток и товар в пути → дефицит → правило отгрузки → рекомендованный заказ и срочность**. Числа на странице не округляются; `null` показан как «—», а введённый ноль остаётся нулём. Длинные списки документов, доказательства тренда и полные JSON-записи раскрываются на той же странице.

Исходные месячные ячейки восстанавливаются из `source_files` этапа 1 и `source_cells` каждого периода: файл, лист, строка и колонка. Строки документов показывают номер документа и ячейку количества. Данные остатка, товара в пути и правила поставщика содержат собственные ссылки на источник; пользовательский ввод явно отделён от заменённого Excel-снимка и исторического остатка. Исходный Git-коммит и SHA-256 всех восьми входных файлов указаны на странице.

Перед созданием страницы скрипт сверяет бренд/SKU, коммит источника, дату планирования и хеши связей между этапами; затем проверяет арифметику чистого и базового спроса, прогноза, необходимого запаса, дефицита и заказа. При старом или смешанном файле, отсутствующей строке либо ошибочном переходе страница не создаётся — нужно заново пересчитать зависимые этапы. Это локальный аналитический артефакт; общий API-контракт и dashboard пока не меняются.

Флаг `lineage.verified` относится к согласованности сохранённых результатов и их исходных ссылок. Этот скрипт не перечитывает Excel и не выполняет заново оценку выбросов, stockout, тренда или сезонности из первичных строк; за их расчёт и проверку отвечают предыдущие этапы.

## Проверка на исходных данных

Ниже указаны реальные SKU, исходные продажи, прогнозы и правила. **Остатки и товар в пути в двух сценариях с заказом введены вручную для демонстрации; они не являются фактическим складом.** Срок поставки 30 дней и страховой запас 7 дней также заданы как параметры сценария, а не взяты из договора.

| SKU | Что видно по цепочке | Итог |
| --- | --- | --- |
| IEK `010300001_`, исходный снимок | В 2025-05 исключено 44,5 из 72 продаж; в 2025-10 — 56,5 из 89. Необходимый запас 19,0233, в пути 10, текущий остаток не известен. | Ответ о закупке и заказ **недоступны**; исторический остаток не подставлен. |
| IEK `081100277_`, учебный ввод 10 / 0 | База 10,6429; спрос за срок 10,3911 + страховой 2,4246 = необходимый запас 12,8157; дефицит 2,8157; минимум отгрузки 10, исходная ячейка `E60`. | Заказ **10**, риск HIGH, статус `provisional`: смысл минимума требует подтверждения. |
| Systeme `300200851_`, учебный ввод 9 / 0 | База 9,5789; прогноз сентября 10,0579 и октября 10,5368; спрос за срок 10,1599 + страховой 2,3706 = запас 12,5305; дефицит 3,5305; кратность 5 из `E120`. | Заказ **5**, риск HIGH, расчёт по учебному вводу. |

Отдельный локальный пример `300200720_` показывает, почему **нулевой заказ может иметь HIGH-риск**: ввод 3 на складе и 80 в пути покрывает целевой запас, но 3 единиц не хватает на прогноз за срок поставки без своевременного прихода партии.

## Повторить самостоятельно

Сначала подготовьте результаты этапов 1–6 по [инструкции этапа 6](order-recommendation.md). Для исходного снимка IEK без актуального остатка:

```powershell
python backend/trace_sku.py --brand IEK --sku 010300001_
```

Для сценария с ручным вводом из инструкции этапа 6:

```powershell
python backend/trace_sku.py --brand 'Systeme Electric' --sku 300200851_ --sku 300200720_ `
  --balances .analysis/balances/user-input.jsonl `
  --stage5 .analysis/deficit/user-input/all-skus.jsonl `
  --stage6 .analysis/orders/user-input/all-skus.jsonl `
  --output-dir .analysis/trace/user-input
python backend/trace_sku.py --brand IEK --sku 081100277_ `
  --balances .analysis/balances/user-input.jsonl `
  --stage5 .analysis/deficit/user-input/all-skus.jsonl `
  --stage6 .analysis/orders/user-input/all-skus.jsonl `
  --output-dir .analysis/trace/user-input
python -m unittest discover -s backend -p 'test_*.py' -q
```

Откройте `.analysis/trace/user-input/systeme-300200851_.html` либо `iek-081100277_.html`; рядом лежит JSON с полными промежуточными записями. Для другого артикула укажите его точный код 1С через `--sku` и бренд через `--brand`; повторяйте `--sku` для нескольких позиций одного бренда. При изменении остатка сначала повторите этапы 5–6 с новым вводом, затем трассировку. Все результаты остаются в исключённой из Git папке `.analysis/`; файлы партнёра и `main` не изменяются.

После этапа 7 работа останавливается. Dashboard и ввод остатка через UI относятся к этапу 8 и выполняются только по новой команде пользователя.
