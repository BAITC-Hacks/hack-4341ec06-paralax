## Предлагаемый единый внутренний формат

Это схема для следующего этапа, пока без расчёта спроса и без изменения общего API-контракта. Каждая нормализованная запись сохраняет `source_ref = {git_commit, file, sheet, row, column}`. Значения `null` означают неизвестно, а не ноль.

| Сущность | Поля |
| --- | --- |
| `Sku` | `brand`, `sku_1c`, `name`, `supplier_article`, `unit` |
| `DocumentMovement` | `brand`, `sku_1c`, `occurred_at`, `document_number`, `warehouse`, `unit`, `signed_quantity`, `source_ref` |
| `MonthlySales` | `brand`, `sku_1c`, `month`, `quantity`, `source_ref` |
| `MonthlyStock` | `brand`, `sku_1c`, `month`, `quantity`, `snapshot_basis` (`beginning` для IEK, `unknown` для Systeme), `source_ref` |
| `TransitLine` | `brand`, `sku_1c`, `snapshot_date`, `shipment_id`, `expected_arrival` (если указан), `quantity`, `source_ref` |
| `PackingRule` | `brand`, `sku_1c`, `rule_kind` (`minimum_dispatch` или `multiple`), `quantity`, `source_ref` |
| `BrandSeasonalitySource` | `brand`, `year`, `month`, `monetary_value`, `source_ref`; связь с отдельным SKU отсутствует |

Числа из расходных документов пока хранятся **со знаком источника**: в данных есть и положительные, и отрицательные количества. Правило превращения этих строк в продажи будет проверено на этапе 1. Месячные итоги не суммируются со строками документов — это альтернативные представления истории продаж. Дублирующиеся записи одного SKU в документах допустимы; дубли SKU в одном справочном листе требуют проверки.

## Количественная проверка

Проверены все заполненные строки десяти листов, где есть SKU; четыре листа сезонности описаны по структуре.

| Источник | IEK: строк / уникальных SKU | Systeme: строк / уникальных SKU |
| --- | ---: | ---: |
| Документы | 171 604 / 2 151 | 77 313 / 565 |
| Месячные продажи | 2 464 / 2 463 | 555 / 554 |
| Месячные остатки | 2 854 / 2 853 | 701 / 701 |
| В пути | 2 641 / 2 616 | 497 / 497 |
| MOQ / кратность | 1 938 / 1 937 | 555 / 554 |
| Пересечение всех пяти SKU-источников | **1 719** | **467** |

Проблемы, которые импорт должен сохранять как диагностические признаки:

- В нескольких основных листах по одной строке без SKU; в IEK «в пути» таких строк **18**. Их нельзя автоматически приписать товару.
- В IEK MOQ один повтор ключа `270400035_`; в IEK «в пути» **7** повторных строк SKU. Для движения товара повторные строки могут быть несколькими партиями — требуется чтение колонок, а не безусловное удаление.
- Отрицательные числа: в строках документов IEK **115**, Systeme **302**; в месячных продажах IEK **241** ячейка, Systeme **323**; в месячных остатках IEK **5** ячеек. Это не следует молча обнулять.
- Пустые месячные ячейки: продажи IEK **44 626**, Systeme **7 105**; остатки IEK **27 678**, Systeme **5 133**. Пустота не равна подтверждённому нулю.
- Из SKU месячных продаж IEK **702** отсутствуют в MOQ, **379** — в таблице пути, **7** — в остатках. Для Systeme соответственно **0**, **85**, **0**. Обратные несовпадения между остатками и продажами: **397** IEK и **147** Systeme.
- В Systeme файле продаж есть столбец `Кратность`, но он может быть `0` при положительном значении в файле MOQ. Источником правила считаем файл MOQ после проверки конфликтов.
- В Systeme файле «товар в пути» имя содержит `22.09.2026`, а заголовок поля — `СЭ в пути 24.09`. Дату снимка нужно уточнить. Значения `Остаток` в этом файле нельзя приравнивать к сентябрьскому месячному остатку без проверки момента снимка.
- Сезонность дана в **денежном агрегате бренда**, а продажи SKU — в штуках/метрах/упаковках. Сезонный коэффициент для SKU нельзя взять напрямую из этих сумм.
- В нескольких кодах нет завершающего `_`; это не основание для автоматического исправления или исключения. Точное строковое совпадение сохраняется.

Примеры проверяемой связки пяти источников (последний месячный столбец — сентябрь 2026, пустые значения показаны как `null`):

| Бренд / SKU | Строк документов | Продажи, сент. | Остаток, сент. | Правило | В пути / снимок |
| --- | ---: | ---: | ---: | ---: | --- |
| IEK `010300001_` | 26 | 15 | 57 | мин. отгрузка 1 | сумма шести партий: 10 |
| IEK `010300002_` | 189 | 14 | 709 | мин. отгрузка 1 | сумма шести партий: 0 |
| Systeme `010400433_` | 121 | 7 | 65 | кратность 1 | `СЭ в пути 24.09` = 0; `Остаток` = 27; `Свободный остаток` = 27 |

Адреса исходных строк в порядке **MOQ / документы (первые две строки) / месячные остатки / месячные продажи / в пути**: IEK `010300001_` — `208 / 2728, 4047 / 368 / 343 / 146`; IEK `010300002_` — `209 / 369, 1546 / 370 / 345 / 147`; Systeme `010400433_` — `48 / 390, 730 / 111 / 48 / 495`. Полный список первичных ссылок для примеров есть в `coverage.*.examples[*].source_rows` локального JSON.

Сентябрьские месячные величины и снимок «в пути» имеют разную временную базу. Эти примеры показывают связность, **не** рекомендацию заказа.

## Повторить проверку

Из корня репозитория, после `git fetch origin`:

```powershell
python -m pip install -r backend/requirements.txt
python backend/inspect_workbooks.py
python backend/audit_sources.py
Get-Content .analysis/source-audit.json -Raw -Encoding UTF8
```

Скрипты читают `origin/main` через `git show`, только если там доступен указанный набор Excel. При изменении `origin/main` сверяйте `ref_commit` в JSON с хэшем выше: числа в этом отчёте относятся к конкретному коммиту. Никакие Excel-файлы и ветка `main` командами не изменяются.
