# Этап 1 — чистый спрос

Расчёт реализован в `backend/clean_demand.py` для всех SKU IEK и Systeme Electric. Источник зафиксирован на Git-коммите `a7a1d3bcd25ab137eac7915f29a4e5c2f5a0f5bc`; код читает Excel через `git show`, не меняя книги и `main`. Результат этапа сохраняется **локально** в игнорируемой папке `.analysis/clean-demand/`, потому что это производные данные партнёра. Общий контракт `contracts/` не менялся.

## Правило

Для каждого месяца с непустой ячейкой продаж:

`observed_demand = max(0, raw_sales)`

`clean_demand = observed_demand − excluded_one_off + estimated_lost_demand`

`raw_sales` всегда сохраняется со знаком, включая отрицательные месяцы (возможные возвраты); преобразование отрицательного итога в ноль отмечается причиной `negative_net_sales_return`. Пустая ячейка остаётся `null`, а не нулём. Если её удаётся восстановить при возможном stockout, `clean_demand` получает оценку; иначе остаётся `null`.

Для одного SKU порог крупной **положительной строки документа** вычисляется по документам в совпадающей единице измерения. Требуется не менее 8 положительных строк. Используются медиана, MAD и IQR:

`threshold = max(4×median, median + 6×1.4826×MAD, Q3 + 3×IQR, median + 5)`.

Строка выше порога помечается как возможный разовый заказ. Предлагаемое исключение — только часть её количества сверх медианного документа, а не удаление всей строки. Месячные продажи из Excel — источник `raw_sales`; сумма строк документов за этот месяц проверяется отдельно. Исключение применяется лишь если сумма документов и месячный итог отличаются не более чем на `max(2 единицы, 5% от большей абсолютной суммы)`. Иначе документ сохраняется в трассировке с причиной `one_off_document_unreconciled_no_exclusion`, а `excluded_one_off = 0`. Исключение не может превысить наблюдаемый спрос. ID клиента отсутствует, поэтому концентрацию по клиенту проверить нельзя.

Возможный stockout оценивается **только при числовом нуле остатка** и месячных продажах не выше 25% нормального уровня (или их отсутствии). Нормальный уровень — медиана до шести ближайших месяцев в пределах ±6 месяцев с положительным остатком и положительным очищенным спросом; нужно минимум два таких месяца. При достаточной истории (12 нормальных месяцев и два наблюдения того же календарного месяца) применяется коэффициент сезонности **самого SKU**, ограниченный диапазоном 0,5–1,5. Иначе коэффициент равен 1. Нулевой остаток на начало месяца IEK — лишь признак возможного дефицита, не доказательство отсутствия товара весь месяц. Пустой или отрицательный остаток не даёт права на восстановление. Денежную агрегированную сезонность бренда к штукам/метрам SKU не применяем.

Сентябрь 2026 помечен как неполный период: документы заканчиваются 22.09.2026, поэтому низкие продажи и нулевой остаток в этом месяце не используются для оценки stockout и сезонной базы. Месяц остаётся в трассировке.

## Реальная проверка

Полный прогон охватывает **3 561 SKU** (2 860 IEK, 701 Systeme Electric) и по 33 месячных периода на SKU. Верифицированы **2 986 периодов** с вычетом документного выброса после сверки итогов (2 735 IEK, 251 Systeme). Ещё **2 051** месяц с подозрительной крупной строкой не скорректирован из-за расхождения источников. В месячных рядах **69 683** пустых ячеек продаж среди объединённого множества SKU, включая товары только из остатков/документов. Числовых нулей в месячных остатках источника не найдено, поэтому на реальных книгах **нет обоснованного восстановления stockout**; `estimated_lost_demand = 0` во всех реальных периодах. Это ограничение исходных данных, а не вывод о том, что упущенного спроса не было.

| SKU и период | Raw sales | Документы за месяц | Исключено | Восстановлено | Clean demand | Объяснение |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| IEK `010300001_`, 2025-05 | 72 | 72 | 44,5 | 0 | 27,5 | Крупный документ; итоги источников совпали |
| IEK `010300002_`, 2025-05 | 331 | 632 | 0 | 0 | 331 | Крупный документ найден, но источники расходятся |
| Systeme `010400433_`, 2026-08 | 72 | 73 | 58 | 0 | 14 | Два крупных документа; расхождение 1 в пределах допуска |

Для этих строк адреса в исходных книгах: IEK `010300001_` — продажи `Лист_1` строка 343, колонка 19; остаток строка 368, колонка 20; крупный документ строка 34600. IEK `010300002_` — продажи строка 345, колонка 19; документы 31758, 33353, 33526. Systeme `010400433_` — продажи строка 48, колонка 36; документы 71154 и 71440. Пути к книгам и остальные координаты находятся в JSON-трассировке.

Для каждого SKU JSON сохраняет все учтённые строки документов с номерами исходных строк. Для каждого периода он сохраняет координату исходной месячной ячейки, документы-выбросы, порог и медиану по SKU, месячную сумму документов, базовые месяцы и коэффициент сезонности для восстановления, а также машинные причины решения. Таблица и график `raw sales vs clean demand` генерируются в локальном HTML для выбранного SKU. Строки Excel не удаляются и не редактируются.

## Проверить самостоятельно

Из корня ветки `feat/codex/backend` с доступным коммитом данных:

```powershell
python -m pip install -r backend/requirements.txt
python -m unittest discover -s backend -p 'test_*.py' -v
python backend/clean_demand.py --sku 010300001_ --sku 010300002_ --sku 010400433_
```

Затем открыть `.analysis/clean-demand/iek-010300001_.html` или другие два HTML-файла. Рядом есть CSV-таблицы и подробные JSON-трассировки. `.analysis/clean-demand/all-skus.jsonl` содержит все SKU; каждая строка — самостоятельный JSON-объект с 33 периодами. Для другого SKU повторить команду с его кодом; при совпадении кода у двух брендов можно добавить `--brand IEK` или `--brand "Systeme Electric"`.

Автоматические тесты используют только синтетические данные: большой разовый документ, расхождение источников, нулевой остаток с нулевыми продажами, сезонную поправку, пустой остаток/неполный месяц и отрицательные продажи.
