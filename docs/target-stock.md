# Этап 4 — необходимый запас

`backend/target_stock.py` берёт помесячный прогноз этапа 3 и для каждого SKU считает запас, необходимый на время ожидания новой поставки. Этап **не рассчитывает дефицит или заказ**: текущий остаток, товар в пути, MOQ и срочность относятся к последующим этапам.

## Параметры и формула

Дата начала планирования (`planning_date`), срок поставки (`lead_time_days`) и запас в днях (`safety_stock_days`) задаются **явно** при запуске. Договорного срока поставки в исходных книгах нет. Даты прибытия уже находящихся в пути партий IEK не являются сроком новой поставки. Значения 30 и 7 дней ниже — только параметры демонстрационного сценария, а не подтверждённые условия поставщика.

Горизонт — полуоткрытый календарный интервал `[planning_date, planning_date + lead_time_days)`: начальный день входит, конечный не входит. Месячный прогноз равномерно распределяется по календарным дням соответствующего месяца. Для каждого пересечённого месяца сохраняются прогноз за полный месяц, число дней в нём, число дней внутри горизонта и вклад:

```text
вклад месяца = прогноз полного месяца × покрытые дни / дни в месяце
спрос за срок поставки = сумма вкладов месяцев
средний дневной прогноз = спрос за срок поставки / lead_time_days
страховой запас = средний дневной прогноз × safety_stock_days
необходимый запас = спрос за срок поставки + страховой запас
```

Например, `[2026-09-23, 2026-10-23)` включает 8 дней сентября и 22 дня октября. Прогноз сентября этапа 3 относится ко **всему** сентябрю; в расчёт входит только `8/30` этого прогноза. Доли месяцев и итог хранятся без округления, чтобы следующий этап мог использовать точные числа. Округление закупки и MOQ здесь не применяются.

Если прогноз покрываемого месяца равен `null`, итог имеет статус `unavailable`, а неизвестное значение не подменяется нулём. Если месяц отсутствует в выходе этапа 3, расчёт завершается явной ошибкой с предложением продлить горизонт прогноза; частичный результат не принимается. Нулевой числовой прогноз остаётся достоверным нулём. Результат сохраняет SHA-256 входного файла этапа 3 и идентификаторы его исходных этапов для трассировки.

## Результат на данных

Для сценария `planning_date=2026-09-23`, `lead_time_days=30`, `safety_stock_days=7` обработан **3 561 SKU**; у **554** прогноз или базовый спрос недоступен, поэтому необходимый запас имеет статус `unavailable`.

| Бренд / SKU | Сентябрь: 8/30 | Октябрь: 22/31 | Спрос за 30 дней | Страховой запас | Необходимый запас |
| --- | ---: | ---: | ---: | ---: | ---: |
| IEK `010300001_` | 2,4068736575 | 13,0174046148 | 15,4242782723 | 3,5989982635 | **19,0232765358** |
| IEK `010300002_` | 16,9395593541 | 27,9850372531 | 44,9245966072 | 10,4824058750 | **55,4070024822** |
| Systeme Electric `010400433_` | 2,2091087816 | 9,4576501485 | 11,6667589301 | 2,7222437504 | **14,3890026805** |

Показанные значения иллюстрируют расчёт **только при заданных параметрах**; они не являются рекомендованным количеством к заказу. Полная точность и ссылки на входной прогноз доступны в локальных JSON-результатах.

## Повторить и проверить

Из корня ветки `feat/codex/backend` сначала выполните этапы 1–3, если локальных JSONL ещё нет:

```powershell
python -m pip install -r backend/requirements.txt
python backend/clean_demand.py
python backend/base_demand.py
python backend/forecast_demand.py
```

Затем запустите этап 4 для полного набора и трёх удобных примеров:

```powershell
python backend/target_stock.py --planning-date 2026-09-23 --lead-time-days 30 --safety-stock-days 7 --sku 010300001_ --sku 010300002_ --sku 010400433_
python -m unittest discover -s backend -p 'test_*.py' -v
```

Выход всех SKU находится в `.analysis/target-stock/all-skus.jsonl`. Для выбранных SKU рядом создаются отдельные `.json`, `.csv` и `.html`; например, `.analysis/target-stock/iek-010300002_.html` показывает месячные доли и итог. Эти производные данные партнёра исключены из Git. При использовании другого Python нужно установить `openpyxl` из `backend/requirements.txt`; bundled Python среды Codex уже содержит зависимость.

Семь синтетических unit-тестов этапа 4 проверяют частичные и целые месяцы, високосный февраль, нулевые и дробные прогнозы без округления, неизвестный прогноз, отсутствующий месяц и некорректные параметры. Вместе с тестами этапов 1–3 прошло **26 тестов**.

Ограничение: для Systeme Electric единая подтверждённая дата актуальности всех исходных таблиц не установлена. `planning_date` в примере — дата сценария, а не доказанная дата единого снимка. Страховые 7 дней и срок 30 дней также требуют подтверждения для реальной закупки.
