# MVP: рекомендации заказов поставщикам

Статус: **логистический трек выбран командой; детали реализации предварительные**. Формат данных партнёра, стек и формула ещё не подтверждены. Источник условий — кейс ТОО «Электрокомплект», краткое изложение в корневом `README.md`.

## Проблема, пользователь и ценность

Менеджер закупок сводит продажи и остатки вручную. Разовые крупные продажи завышают регулярный спрос, а периоды без товара скрывают упущенный спрос. MVP предлагает проверяемые количества пополнения и группирует черновики заказов по поставщикам. Менеджер видит причины расчёта, может изменить количество и утверждает результат сам.

Подтверждение проблемы: формулировка партнёра в кейсе; количественные показатели экономии и точности пока не предоставлены. Не обещать их в демо как измеренный результат.

## Демо за 60–90 секунд

1. Запустить расчёт на синтетической выборке и открыть три артикула: обычный, с периодом отсутствия и с разовой крупной продажей.
2. Показать количество и вклад прогноза, страхового запаса, остатка и товара в пути.
3. Увеличить товар в пути: рекомендация уменьшается. Показать, что разовая продажа помечена и не раздувает регулярный заказ.
4. Открыть группировку по поставщику, скорректировать строку, утвердить черновик и экспортировать его без автоматической отправки поставщику.

## Основной путь пользователя и критерии приёмки

1. Менеджер загружает/выбирает валидный набор продаж, остатков, товаров в пути, периодов отсутствия, каталога и поставщиков. Ошибка схемы сообщает конкретное поле и не запускает расчёт.
2. Система строит регулярный спрос по каждому артикулу, учитывает категорию, сезонность, устойчивый рост и заданный прогноз прироста. Изменение соответствующих данных меняет объяснимые компоненты результата.
3. Разовая крупная продажа одному клиенту отмечается отдельно. Добавление такой продажи не должно существенно повышать прогноз регулярного спроса на тестовом сценарии.
4. Для периода отсутствия товара оценивается упущенный спрос. При прочих равных скорректированная потребность выше расчёта по сырым продажам.
5. Количество заказа неотрицательно и учитывает текущий остаток, товар в пути и срок поставки. При увеличении товара в пути количество заказа не растёт.
6. Результат содержит артикул, склад, поставщика, рекомендованное количество, срочность и числовое обоснование; доступна группировка по поставщику.
7. Менеджер может отредактировать количество, подтвердить черновик и экспортировать его. Отправка поставщику не происходит.

Ключевые проверки записаны также в `fixtures/scenarios.md`. Структуры входа и выхода определены в `contracts/`.

## Границы MVP

- Один склад за один запуск, несколько артикулов и поставщиков. Демо основано на синтетических обезличенных данных.
- Загрузка CSV/XLSX или встроенной фикстуры выбирается после решения по стеку. Канонический формат обмена между частями приложения — JSON из `contracts/`.
- Формула должна быть зафиксирована до написания расчётного кода и сверена с доступной историей. Временной горизонт заказа: срок поставки плюс период пересмотра; количественные параметры страхового запаса и правила выбросов пока открыты.
- Материальная ведомость 1С требует согласования семантики: нельзя дважды учитывать одни и те же потребности. До этого адаптер 1С не входит в демо-контракт.
- LLM API может объяснять уже вычисленные факты на синтетических данных. Без ответа API числовой расчёт и текстовое обоснование по правилам продолжают работать.

## Вне объёма

Реальная интеграция с 1С, автоматическая отправка заказов, обучение модели, точное обещание сокращения запасов, сложная оптимизация по всем складам и промышленная авторизация.

## Риски и запасной сценарий

- Полная выгрузка и дата её выдачи неизвестны: использовать версионированные синтетические фикстуры, затем адаптировать импорт.
- Короткая история не доказывает годовую сезонность: показывать её только на достаточной синтетической истории и помечать уверенность расчёта.
- LLM может ошибиться в тексте: числовые поля формирует только движок, ответ API проверяется, а при сбое остаётся шаблонное объяснение.

## Definition of Done

Работает путь от данных до утверждённого экспортируемого черновика; проходят проверка схем, ключевые acceptance-проверки и команда `check` после выбора стека; инструкция запуска точна; секретов и реальных данных клиентов нет; есть демо-артефакт и фактические ежечасные отчёты участников.

## План на 5 часов

`00:00–00:30` — подтверждение трека, владельцев, стека и контракта. `00:30–01:20` — фикстуры, проверка схем, первые acceptance-тесты. `01:20–03:55` — расчёт, интерфейс и экспорт в личных ветках. `03:55–04:30` — интеграция. `04:30–05:00` — полный прогон и защита. Имена владельцев фиксируются в `docs/tasks.md` после распределения.
