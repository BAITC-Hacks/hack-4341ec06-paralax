# ТЗ и спецификация MVP: рекомендации заказов поставщикам

Статус: **трек выбран, ТЗ готово к обсуждению, разработка ещё не начата**. Этот файл — источник истины для участников и их ИИ-сессий. Изменение обещанного поведения сначала фиксируется здесь, затем в `contracts/`, тестах и коде. Обзор исходного кейса находится в корневом `README.md`; рабочие правила — в `AGENTS.md`.

## 1. Контекст, проблема и цель

Трек HackAlem AI: автоматизация формирования заказов поставщикам для ТОО «Электрокомплект». Менеджер закупок вручную сводит продажи и складские данные в Excel. Разовые крупные продажи могут завышать оценку регулярного спроса; периоды отсутствия товара могут скрывать спрос; закупка без учёта остатков и товаров в пути ведёт к излишку или дефициту. Это утверждения из кейса партнёра; измеренный экономический эффект пока не предоставлен.

Цель MVP — дать менеджеру **проверяемый черновик пополнения**: сколько единиц каждого артикула заказать у какого поставщика, какие данные и допущения привели к числу, что требует ручной проверки. Менеджер может изменить количество, утвердить черновик и выгрузить его. Система не отправляет заказ поставщику сама.

Основной пользователь — менеджер отдела закупок. Вторичный пользователь — руководитель, который проверяет основания заказа. Демонстрация строится на одном поставщике, IEK; архитектура должна позволять позднее подключить Systeme Electric.

В переданном кейсе нет отдельной таблицы баллов жюри для этого трека. Приоритеты ниже выведены из обязательных требований; если организаторы дадут критерии оценки, команда добавит их в этот раздел до изменения объёма работы.

## 2. Данные и проверенные ограничения

В локальной папке `data/` лежат 12 Excel-книг по IEK и Systeme Electric: помесячные продажи и остатки за 2024–2026 годы, отдельные продажи по документам, товары в пути, сезонность и MOQ/кратность. Папка сейчас не отслеживается Git; исходные книги не включать в коммиты до проверки разрешения партнёра. Для общих тестов использовать синтетические данные и малые обезличенные примеры.

Ключ связи между книгами — **код номенклатуры 1С**; хранить его строкой, включая завершающие символы. Названия товара могут отличаться и не служат ключом. Адаптер должен явно записывать источник, дату среза, единицу измерения и охват склада/филиалов.

Для первого реального расчёта нужны помесячные продажи и остатки IEK, отдельные продажи по документам и файл товаров в пути. Книга сезонности служит контрольным источником; правила MOQ подключаются после проверки их смысла. Если один из первых четырёх источников нельзя связать по коду 1С, демо переключается на синтетическую фикстуру с теми же полями.

Обнаруженные пробелы:

- В книге отдельных продаж есть дата, номер документа, код, наименование, единица, склад и количество. Нет явных `customer_id` и цены. Можно отметить крупный документ, но нельзя доказать, что несколько документов принадлежат одному клиенту.
- Отдельного достоверного журнала интервалов stockout в переданных файлах нет. Нулевой месячный остаток — признак возможного дефицита, а не доказательство точного числа дней без товара.
- Месячный остаток не следует автоматически выдавать за актуальный остаток на дату файла товаров в пути. Даты и охват надо показать в UI.
- Срок поставки, внешняя оценка прироста спроса и семантика материальной ведомости 1С требуют подтверждения партнёра. Для демо они могут быть явно заданными параметрами, помеченными как допущения.
- «MOQ» и «кратность отгрузки» не считать одним правилом без проверки заголовков и смысла данных.

Текущий `contracts/planning-input.schema.json` — версия 0.1.0 для синтетического сценария: он требует `customer_id`, `unit_price_kzt`, точные интервалы stockout и `warehouse_id`. **Он ещё не подходит для прямого импорта выданных Excel.** До написания импортера владелец контракта выпускает следующую версию: документ вместо недоступного клиента, необязательная цена, явный признак достоверности stockout и корректный охват остатков. Нельзя молча подставлять фиктивные значения в обязательные поля.

## 3. Предлагаемый стек и границы компонентов

- Backend: Python, `pandas`/`openpyxl` для Excel, FastAPI для API и серверного вызова OpenAI.
- UI: React + TypeScript + Vite. Участник UI начинает с валидной фикстуры результата и работает независимо от импортера.
- Контракт: версия JSON Schema для входа и результата; backend валидирует данные, UI использует согласованные типы. Формат адаптера Excel может меняться, канонический смысл полей — только через контракт.
- Хранение MVP: файлы нормализованного демо-набора и локальное состояние черновика; выбор SQLite допустим, если без него не обеспечить повторное открытие утверждённого черновика. Не строить регистрацию или промышленную БД.

Поток: `Excel → адаптер и проверка → нормализованные записи → расчёт → числовые факторы → API → UI → ручная правка/утверждение → CSV`. Ветвь AI получает только проверенные факторы расчёта и готовит объяснение; она не меняет вычисленные количества.

## 4. Расчётный сценарий

Пользователь открывает заранее подготовленный нормализованный набор IEK, выбирает категорию или список артикулов и запускает расчёт. Для каждого артикула движок:

1. Приводит продажи к единым датам и единицам; проверяет дубликаты и наличие кода 1С.
2. Отмечает кандидатов на разовые крупные продажи по объёму документа относительно истории того же артикула. Исходная продажа сохраняется; регулярный прогноз использует отдельно задокументированное правило обработки аномалии. При короткой истории выводится флаг неопределённости.
3. Оценивает регулярный спрос. По двум годовым циклам может рассчитать месячную сезонность; при недостаточной истории использует нейтральный коэффициент или аккуратный коэффициент категории с пометкой источника. Устойчивый рост определяется по нескольким периодам, а не по одному всплеску.
4. Если есть подтверждённый интервал stockout, оценивает упущенный спрос по сопоставимым периодам. Для нулевых месячных остатков из текущих книг показывает **гипотезу дефицита** и диапазон/флаг неопределённости; не называет число упущенных продаж измеренным фактом.
5. Применяет явно заданный прогноз прироста, срок поставки и период пересмотра. Все значения и источники видны пользователю.
6. Считает: `горизонт = срок поставки + период пересмотра`; `заказ = max(0, ceil(прогноз на горизонт + страховой запас − текущий остаток − товар в пути))`. Правило страхового запаса, округления и пороги аномалий фиксируются в `docs/decisions.md` и исполнимых тестах до реализации.
7. Определяет срочность по ожидаемому покрытию спроса остатком и сроку поставки. Объяснение содержит именно использованные компоненты, а не общее «AI рекомендует».

Для первой демо-версии допустимо рассчитать 20–50 выбранных артикулов IEK из реальной структуры файлов и синтетические крайние случаи. Остальная выгрузка не должна требовать иной формы данных. Производительность полного набора измеряется отдельно, если остаётся время.

## 5. Функциональные требования и приёмка

**FR-01. Вход и валидация.** Адаптер читает выбранные книги, связывает записи по коду 1С, сохраняет единицу и дату среза. Отсутствующий обязательный источник, дубль ключа или неверная единица дают понятную ошибку. Фикстуры проходят JSON Schema-валидацию.

**FR-02. Базовый заказ.** Результат по каждому артикулу содержит поставщика, прогноз, остаток, товар в пути, горизонт, страховой запас, рекомендуемое целое количество и срочность. При прочих равных увеличение товара в пути не увеличивает заказ; количество не бывает отрицательным.

**FR-03. Аномалия.** Разовая крупная отгрузка помечается. На контрольной фикстуре она не увеличивает регулярную закупку пропорционально размеру выброса. Без ID клиента UI пишет «крупный документ», а не «заказ одного клиента».

**FR-04. Сезонность и рост.** На фикстуре с двумя повторяющимися сезонами прогноз высокого сезона выше низкого. Последовательный рост нескольких периодов меняет прогноз; одиночный всплеск не считается устойчивым ростом. Когда данных мало, UI показывает допущение.

**FR-05. Дефицит.** Подтверждённый stockout повышает оценку потребности относительно расчёта по сырым продажам. Предполагаемый stockout из месячных остатков помечается отдельно.

**FR-06. Просмотр и правка.** UI показывает сводку, фильтры, группировку по поставщику, таблицу и детальный разбор одной строки. Менеджер может изменить `selected_quantity`; `recommended_quantity` остаётся видимым для сравнения. Пустой результат, загрузка и ошибка имеют явные состояния.

**FR-07. Решение человека.** Черновик становится `approved` только по явной кнопке. Экспорт CSV содержит поставщика, код, название, исходное и выбранное количество, статус и дату расчёта. Экспорт не отправляет заказ автоматически.

**FR-08. AI-объяснение.** По запросу пользователя OpenAI API выдаёт короткое объяснение факторов, риска и вопроса для проверки менеджером. Ответ привязан к переданным числам и источникам; при сбое или неподходящем ответе показывается детерминированное объяснение. Проверка: модель не изменяет рекомендованное количество и не добавляет отсутствующие факты.

## 6. OpenAI API: роль, вход, выход и ограничения

API вызывается **только backend-сервером**. Ключ берётся из переменной окружения `OPENAI_API_KEY`, модель — из конфигурации после проверки доступа команды. Использовать Responses API со структурированным JSON-ответом и серверной валидацией; официальный подход к Structured Outputs описан в [документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

Вход одного вызова: артикул или синтетический идентификатор, дата среза, вычисленные факторы и их единицы, флаги источника/неопределённости, рекомендованное количество. Не отправлять исходные книги, документные номера и реальные данные партнёра во внешний API без отдельного разрешения. Для первого сквозного демо достаточно синтетических или безопасно агрегированных значений.

Ожидаемый JSON: `summary`, `drivers[]`, `risk`, `review_question`, `evidence_keys[]`. Поле `evidence_keys` содержит только ключи факторов, реально переданных модели. Числа в тексте сверяются с факторами; неподтверждённая строка отбрасывается. Промпт и пример корректного/некорректного ответа версионируются вместе с кодом. При таймауте, ошибке API или невалидном JSON UI показывает расчёт и шаблонное объяснение без остановки работы.

В качестве дополнительной AI-функции после основного пути можно предложить менеджеру сравнение двух уже пересчитанных сценариев («если товар в пути увеличится на N»), но любое альтернативное количество заново вычисляет движок.

## 7. UI и демо-сцена

Экран минимальный: выбор демо-набора и категории, кнопка «Рассчитать», сводка по количеству позиций/поставщиков, таблица рекомендаций, панель факторов выбранного артикула, поле ручной правки, кнопки «Утвердить» и «Экспортировать». На панели факторов видны дата и источник остатка, прогноз, срок поставки, товар в пути, поправка на аномалию/дефицит и AI-объяснение. Цвет не заменяет текстовый статус.

Демо за 60–90 секунд: запустить набор; показать крупную отгрузку и её флаг; открыть позицию с недостаточным остатком; увеличить товар в пути и увидеть уменьшение рекомендации; получить AI-объяснение конкретных чисел; вручную изменить количество; утвердить черновик и открыть CSV. Если API недоступен на защите, показывается честно подписанный резервный текст и работающий расчёт.

## 8. Границы объёма и дополнительные возможности

В MVP входят FR-01–FR-08 для одного бренда и подготовленного набора. Не входят обучение модели, прогноз прибыли, полная интеграция с 1С, автоматическая отправка поставщику, регистрация, сложные права доступа, множество складов и производственное развёртывание.

После работающего MVP можно добавить в таком порядке: кратность/MOQ после проверки смысла поля; сравнение простого и скорректированного прогноза; график продаж и остатков; второй бренд; импорт произвольной книги из UI; сравнение сценариев и отдельный экран контроля качества данных. Новую возможность добавлять только если сквозной сценарий и `check` зелёные.

## 9. Направления работы трёх участников

**Участник UI.** Владеет `frontend/`: React-экран, таблица, фильтры, детальная панель, редактирование, состояния загрузки/ошибки, экспортная кнопка, frontend lint/typecheck/build. Начинает с валидной фикстуры `PlanningResult`; не меняет общий контракт без согласования. Проверяемый результат — пользователь может пройти сценарий на моковом API, затем на реальном backend.

**Участник данных.** Владеет импортерами и расчётным модулем в `backend/`, а также тестами своей логики и проверками формата Python. Связывает Excel по коду 1С, документирует охват и дату, реализует обработку крупных документов, сезонности, тренда, дефицита и формулу заказа. Проверяемый результат — одинаковый вход даёт одинаковый результат; ключевые сценарии проходят тесты.

**Участник API и интеграции.** Владеет `contracts/`, `fixtures/`, API, модулем OpenAI и общей командой `check`/CI, которая вызывает проверки UI и данных; объединяет проверенные ветки по согласованию команды. Не подменяет реальный вклад двух других участников. Проверяемый результат — UI получает валидный `PlanningResult`, AI-ошибка не ломает расчёт, приложение запускается по README.

Имена участников и реального интегратора заносятся в `docs/tasks.md` до начала кодирования. Каждый работает в собственной ветке `feat/<member>/<task>` и отдельном клоне/worktree, делает маленькие коммиты и ежечасный фактический отчёт в `docs/updates/<member>/`.

## 10. Quality harness: обязательная подготовка, текущий статус

**Сейчас не подключён.** В репозитории есть JSON-схемы, пример фикстуры и текстовые сценарии, но нет исполнимых тестов, `check`, formatter/linter/typecheck/build и GitHub Actions. `.env.example` уже есть; он не содержит ключа.

После выбора и установки стека, **до основной реализации**, добавить:

- проверку контрактов и фикстур;
- 3–5 исполнимых acceptance-тестов требований FR-02–FR-05 и FR-07;
- unit-тесты формулы, аномалии, дефицита, сезонности и округления;
- один smoke-тест пути API → UI/экспорт, если его настройка укладывается в срок;
- форматирование Python и TS, lint, typecheck, тесты, frontend build;
- одну корневую команду `check`, которая запускает проверки в стабильном порядке, и GitHub Actions с этой же командой.

Рабочий цикл: требование → падающий тест → реализация → зелёный тест. Тест меняется вместе с требованием в этом документе, не ради прохождения. «Harness» здесь означает **проверки проекта**; управляемый Codex Harness и Agents API не требуются для этого приложения.

## 11. План 5 часов и ежечасные результаты

- `00:00–00:30`: записать имена/ветки и стек, сопоставить Excel с контрактом, утвердить допущения о сроке поставки, запасе и дефиците. Результат: исправленный контракт и карта полей.
- `00:30–01:20`: валидные синтетические фикстуры, первые падающие acceptance-тесты, команда `check`, минимальный API и UI на моках. Результат: проверяемый каркас.
- `01:20–03:55`: параллельно импорт и расчёт, UI, интеграция OpenAI. Каждый час — работающий промежуточный сценарий, коммит или draft PR, результаты проверок и демо-артефакт при наличии.
- `03:55–04:30`: последовательное объединение личных веток интегратором, исправление контрактных расхождений и полный `check`.
- `04:30–05:00`: чистый запуск по README, повтор демо без подсказок разработчиков, резервный пример при сбое API, подготовка питча.

Если первые 30 минут показывают, что выданные данные нельзя безопасно связать, перейти на версионированную синтетическую фикстуру с той же структурой и честно отметить границу доказательства.

## 12. Definition of Done и оставшиеся решения

Готово, когда FR-01–FR-08 проходят на демо-наборе, UI и API работают совместно, результат можно вручную поправить/утвердить/экспортировать, числовые компоненты объясняют заказ, ошибки API и данных обработаны, `check` и CI зелёные, README содержит точные команды запуска, в Git нет ключей и неразрешённых партнёрских данных, есть демо-артефакт и фактические отчёты участников.

Перед первым кодовым коммитом команда подтверждает: имена и зоны ответственности; окончательный стек; точный охват остатков; значения срока поставки и страхового запаса для демо; правила аномалий/сезонности/stockout; можно ли публиковать производные данные партнёра. Эти решения записываются в `docs/decisions.md`. Если критерии жюри отличаются от переданного кейса, добавить их сюда до изменения объёма MVP.
