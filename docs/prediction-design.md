# Расчёт 0.2.0: решение для текущей части команды

Запрос пользователя от 23.09.2026 разрешает адаптировать mock и входной контракт.
Изменения аддитивные: старые синтетические входы/выходы остаются валидными.
Выходной UI-mock не переписывается. Новые результаты содержат diagnostics,
source_files и assumptions. Эта работа не реализует HTTP/UI другого участника.

## Источники и выбор подхода

Официальная документация проверена 23.09.2026; возможности продуктов могут меняться.

| Решение | Подтверждённые возможности | Решение для MVP |
| --- | --- | --- |

| [frePPLe stockout](https://frepple.com/docs/current/examples/forecasting/forecast-with-missing-data.html) | Пропуски/дефицит нельзя приравнивать к нулевому спросу | Пропуски остаются null; подтверждённый дефицит корректируется отдельно |

## Правила версии

1. IEK: месяц продаж берётся из заголовка; незавершённый сентябрь исключён.
   Пустая ячейка продаж/остатка — неизвестное значение. Документные продажи не
   суммируются повторно с месячными. Отрицательные строки сохраняются в аудите,
   но не становятся положительным спросом через abs().
2. Для демо отбираются первые по коду 1С позиции с достаточной историей,
   известным начальным остатком сентября и записью в транзите, единицей «шт».
   Метры/упаковки требуют подтверждённой конверсии и пока исключены.
   Повторяющиеся коды в транзите исключаются целиком с перечнем в аудите.
   Позиции с пустыми количествами, дублями или несовместимыми единицами
   документов также исключаются целиком, затем выборка дополняется до лимита.
   В проверке сезонного кандидата допускается один предыдущий цикл, но для
   финального выбора необходимо два цикла в доступной истории.
3. Пустая ячейка в существующей строке матрицы заказов в пути принимается как
   отсутствие заказа по этой колонке: явное сценарное допущение.
   Поступления после горизонта не уменьшают заказ. ETA — обещанная верхняя дата.
4. В документной истории кандидат аномалии: объём >5 медиан положительных
   документов за предыдущие 30 дней при наличии >=3 документов. Превышение
   над медианой ограничивается только когда сумма документов месяца совпадает
   с месячной продажей. Иначе остаются флаг и предупреждение о расхождении.
5. Месячные модели: среднее последних 6 наблюдений, SES(alpha=0.3),
   ограниченный устойчивый тренд, сезонный профиль после двух полных циклов,
   TSB(alpha=beta=0.2) только при полной истории с >=30% явных нулей.
   Выбор по MAE в единицах/день на последних до 6 наблюдениях с расширяющимся
   окном; каждый прогноз использует только предшествующие месяцы. После выбора
   модель пересчитывается по всей доступной истории. Это внутренняя валидация
   для выбора модели, а не независимая оценка точности на будущем.
6. Нулевой начальный остаток даёт suspected_stockout и неизвестный упущенный
   спрос (число коррекции 0 с предупреждением). Подтверждённые интервалы
   исключаются из доступной экспозиции; пересекающиеся дни учитываются один раз.
   Ноль продаж при нулевом остатке помечается как неизвестный спрос.
7. Сценарные lead_time=14, review=14, safety=7 дней и рост=0%; редактируются.
   Сезонность усредняется по календарным дням будущего горизонта. Заказ:
   ceil(max(0, forecast+safety-stock-eligible_transit)); затем MOQ/кратность,
   только если заданы явно. MOQ-файл с заголовком «мин.кол.» не доказывает кратность.
8. Остаток 01.09.2026 не пересчитывается в остаток 22.09 без журнала поступлений.
   Охват книг не подтверждён. JSON — сценарный черновик с предупреждениями,
   не готовый к отправке заказ. Утверждение остаётся действием менеджера.
9. OpenAI выбирает только ключи факторов и разрешённые коды риска/вопроса.
   Backend строит summary/drivers/risk/review_question/evidence_keys из словаря
   и фактических чисел: произвольные утверждения модели не попадают в объяснение.
   Без ключа/модели, при ошибке или отказе возвращается fallback. Реальные данные
   не отправляются без отдельного allow_partner_data=True; номера документов,
   названия товаров, файлы и SKU не передаются даже с этим разрешением.
