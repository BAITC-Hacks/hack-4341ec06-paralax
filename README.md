## О проекте

Проект готовится для кейса ТОО «Электрокомплект» в рамках **HackAlem AI**.

Цель — автоматизировать расчёт потребности в пополнении склада и формировать для менеджера отдела закупа рекомендованные заказы поставщикам на основе фактических данных о продажах, остатках, товарах в пути и сроках поставки.

Система не отправляет заказ поставщику автоматически. Финальное решение принимает ответственный сотрудник.

---

## Проблема

Сейчас менеджер отдела закупа рассчитывает потребность в пополнении склада вручную, консолидируя данные в Excel.

Из-за трудоёмкости такого анализа:

- расчёты выполняются нечасто и не в режиме реального времени;
- по части SKU возникают избыточные запасы;
- по другим SKU возникает дефицит;
- разовые крупные продажи искажают регулярный спрос;
- периоды отсутствия товара приводят к недооценке реального спроса;
- компания несёт дополнительные издержки на хранение и теряет продажи из-за stockout.

---

## Ценность решения

Сервис позволяет:

- снизить объём избыточных запасов;
- уменьшить число случаев дефицита;
- сократить упущенные продажи;
- повысить точность закупочных решений;
- учитывать сезонность и устойчивый рост спроса;
- исключать разовые крупные заказы из расчёта регулярной потребности;
- объяснять менеджеру, почему система рекомендует конкретное количество товара.

---

## Пользователь

Основной пользователь — **менеджер отдела закупа**.

### Основной сценарий

1. Менеджер запускает расчёт по складу или категории.
2. Система анализирует входные данные.
3. Для каждого артикула рассчитывается потребность.
4. Система формирует список рекомендованных заказов.
5. Заказы группируются по поставщикам.
6. По каждой позиции показывается краткое обоснование расчёта.
7. Менеджер проверяет рекомендации.
8. При необходимости корректирует количество.
9. Подтверждает заказ.
10. Результат можно экспортировать во внешний формат.

---

## Входные данные

Сервис использует следующие источники.

### История продаж

Минимальные поля:

- дата продажи;
- артикул;
- наименование;
- количество;
- цена;
- обезличенный ID клиента;
- склад.

### Остатки

- текущий остаток по каждому артикулу;
- остаток по складам;
- остаток на дату.

### Stockout

Периоды, когда товар отсутствовал на складе.

Эта информация необходима, потому что фактические продажи во время отсутствия товара не отражают реальный спрос.

### Товары в пути

Количество товара, которое уже заказано у поставщика, но ещё не поступило на склад.

### Поставщики

Справочник поставщиков:

- поставщик;
- артикулы;
- срок поставки;
- дополнительные условия поставки — если доступны.

### Дополнительные данные

- категории товаров;
- прогноз прироста спроса;
- материальная ведомость из 1С.

# Методология расчёта

## 1. Подготовка данных

Перед прогнозированием данные нормализуются и объединяются по артикулу.

Проверяются:

- пропуски;
- дубликаты;
- отрицательные значения;
- некорректные даты;
- аномальные количества;
- непрерывность временного ряда.

Продажи агрегируются по выбранному временному интервалу:

- день;
- неделя;
- месяц.

Рабочий интервал должен определяться в зависимости от объёма и детализации предоставленных данных.

---

## 2. Выявление разовых крупных заказов

Одна из ключевых задач — не позволить крупной единичной продаже искусственно увеличить прогноз регулярного спроса.

Пример:

```text
Обычные продажи:
95, 102, 110, 98, 105

Разовая продажа:
1000
```

Значение `1000` не должно восприниматься системой как устойчивый рост спроса.

### Учитываемые признаки

При обнаружении аномалий могут использоваться:

- размер заказа относительно исторического распределения;
- отклонение от медианного спроса;
- частота аналогичных объёмов в истории;
- доля одного клиента в продажах артикула;
- повторяемость крупного заказа;
- устойчивость изменения спроса во времени.

### Базовый подход

Для MVP рекомендуется использовать устойчивые статистические методы.

Например:

- **IQR — Interquartile Range**;
- **MAD — Median Absolute Deviation**;
- rolling median / rolling statistics.

Пример логики через IQR:

```text
IQR = Q3 - Q1

нижняя граница = Q1 - k × IQR
верхняя граница = Q3 + k × IQR
```

Продажи значительно выше верхней границы рассматриваются как кандидаты на разовый выброс.

Важно: выброс не должен автоматически удаляться. Он должен быть классифицирован системой как потенциально нерегулярный спрос с учётом клиента и истории товара.

---

## 3. Регулярный спрос

После обработки выбросов строится очищенный временной ряд регулярных продаж.

Пример:

```text
Фактические продажи:
100, 105, 98, 110, 950, 102

Регулярный ряд:
100, 105, 98, 110, 102
```

На его основе рассчитывается базовый спрос.

---

## 4. Сезонность

Алгоритм должен учитывать повторяющиеся сезонные изменения.

Примеры:

- рост спроса летом;
- падение зимой;
- регулярный рост определённых категорий в отдельные месяцы.

Простое среднее значение по всей истории использовать недостаточно, если у товара присутствует выраженная сезонность.

Для MVP могут применяться:

- seasonal moving average;
- Holt-Winters;
- Prophet;
- SARIMA;
- другой алгоритм временных рядов, если он обеспечивает объяснимый результат.

Конкретная модель должна выбираться после анализа структуры предоставленного датасета.

---

## 5. Устойчивый рост спроса

Система должна отличать устойчивый тренд от единичного скачка.

Пример:

```text
100 → 110 → 125 → 140 → 155
```

Такой ряд может свидетельствовать о реальном росте спроса.

В отличие от:

```text
100 → 105 → 900 → 98 → 110
```

где `900` с высокой вероятностью является аномальным событием.

При подтверждённом устойчивом тренде прогноз должен корректироваться в сторону роста.

---

## 6. Компенсация stockout

Если товара не было на складе, продажи в этот период искусственно занижены.

Пример:

```text
Обычный спрос: 10 шт./день

5 дней товар отсутствовал.

Фактические продажи за эти дни:
0
```

Нельзя считать, что спрос был равен нулю.

Сервис должен оценить потенциальный упущенный спрос на основе соседних периодов и исторического поведения товара.

Упрощённая логика:

```text
Estimated Lost Demand =
Expected Demand During Stockout
-
Actual Sales During Stockout
```

После этого прогнозируемый спрос корректируется вверх.

# Расчёт рекомендуемого заказа

Концептуально потребность можно представить как:

```text
Recommended Order =
Forecast Demand During Coverage Period
+ Safety Stock
- Current Stock
- Goods In Transit
```

где:

- `Forecast Demand` — прогноз регулярного спроса;
- `Safety Stock` — страховой запас;
- `Current Stock` — текущий остаток;
- `Goods In Transit` — уже заказанный товар;
- `Coverage Period` — период, который должен покрыть новый заказ с учётом срока поставки.

Формула является базовой моделью. Итоговая реализация может корректироваться после анализа реальных данных партнёра.

---

# Срочность заказа

Для каждой позиции система должна определять уровень риска дефицита.

Например:

```text
CRITICAL
HIGH
MEDIUM
LOW
```

В расчёте могут учитываться:

- текущий остаток;
- средний ежедневный спрос;
- прогноз спроса;
- товары в пути;
- срок поставки;
- вероятность stockout до следующей поставки.

---

# Выход системы

Результат отображается в таблице или dashboard.

Пример:

| Артикул | Поставщик | Остаток | В пути | Прогноз | Рекомендуемый заказ | Срочность | Обоснование |
|---|---|---:|---:|---:|---:|---|---|
| SKU-001 | Supplier A | 120 | 50 | 300 | 180 | HIGH | Остатка недостаточно на период поставки |
| SKU-002 | Supplier B | 700 | 0 | 200 | 0 | LOW | Текущего запаса достаточно |
| SKU-003 | Supplier A | 40 | 100 | 280 | 190 | CRITICAL | Высокий риск stockout |

# Explainability

Каждая рекомендация должна иметь объяснение.

Пример:

```text
Рекомендуется заказать: 420 шт.

Причины:
- прогноз спроса на следующий период: 500 шт.;
- текущий остаток: 130 шт.;
- в пути: 100 шт.;
- ожидаемый stockout через 12 дней;
- lead time поставщика: 25 дней;
- обнаружена разовая продажа 800 шт., исключённая из регулярного спроса;
- наблюдается устойчивый рост спроса +8%.
```

Менеджер должен понимать, почему алгоритм получил именно такой результат.

---

# Группировка по поставщикам

Финальный список заказов группируется по поставщику.

Пример:

```text
Supplier A
├── SKU-001 — 180 шт.
├── SKU-003 — 190 шт.
└── SKU-010 — 80 шт.

Supplier B
├── SKU-021 — 500 шт.
└── SKU-032 — 150 шт.
```

Это позволяет сформировать готовый проект заказа для конкретного поставщика.

# Проверка решения

## Test 1 — изменение товаров в пути

Если увеличить количество товара в пути, рекомендуемый новый заказ должен уменьшиться.

```text
goods_in_transit ↑
→
recommended_order ↓
```

---

## Test 2 — сезонность

Для товара с выраженной сезонностью прогноз должен повторять сезонный паттерн, а не рассчитываться только через среднее значение всей истории.

---

## Test 3 — stockout

Если добавить период отсутствия товара, система должна оценить упущенный спрос.

```text
raw sales forecast
<
stockout-adjusted forecast
```

---

## Test 4 — разовый крупный заказ

Если искусственно добавить очень крупную единичную продажу:

```text
100
110
95
105
1000
```

рекомендуемое регулярное количество не должно резко увеличиться только из-за значения `1000`.

---

## Test 5 — поставщики

Финальный список должен группироваться по поставщикам.

Каждая строка должна содержать:

- артикул;
- поставщика;
- рекомендуемое количество;
- срочность;
- объяснение.

# Definition of Done

MVP считается готовым, если:

1. Система принимает тестовый набор данных.
2. Для каждого артикула рассчитывается прогноз спроса.
3. Учитываются остатки и товары в пути.
4. Учитывается сезонность.
5. Учитывается устойчивый рост.
6. Компенсируются периоды stockout.
7. Разовые крупные продажи обнаруживаются и не искажают регулярный прогноз.
8. Формируется рекомендуемое количество заказа.
9. Заказы группируются по поставщикам.
10. Каждая рекомендация содержит объяснение.
11. Результат доступен через таблицу/dashboard.
12. Результат можно экспортировать.
13. Заказ не отправляется поставщику автоматически без подтверждения менеджера.
