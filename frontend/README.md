# Интерфейс закупщика — этап 8

Главный экран React + TypeScript показывает результаты аналитических этапов 1–7 по IEK и Systeme Electric. Он читает локальный API поверх `.analysis/`, а не встраивает данные партнёра в Git. Отдельный прежний UI по синтетическому контракту `PlanningResult` доступен по `/demo`; он может работать с backend из `main` через `VITE_API_BASE_URL`.

## Быстрый запуск

Требуются Python с зависимостями из `backend/requirements.txt`, Node.js 22.18+ и pnpm. Сначала подготовьте результаты этапов 1–6 по инструкциям в `docs/`. Из корня репозитория откройте два терминала:

```powershell
python backend/dashboard_server.py --scenario demo-user-input
```

```powershell
cd frontend
pnpm install
pnpm dev
```

Откройте [http://127.0.0.1:5176/](http://127.0.0.1:5176/). `--scenario demo-user-input` использует ранее подготовленные локальные файлы с **учебными** остатками для трёх SKU; они не являются фактическими данными склада. Без флага сервер берёт исходный снимок: у большинства позиций актуальный остаток неизвестен, и заказ не выдаётся. API доступен только на `127.0.0.1:8777`; Vite передаёт запросы `/api/dashboard`, `/api/stock` и `/api/trace` в него.

## Что проверить

На экране есть сводка по 3 561 SKU, переключение IEK/Systeme, поиск и фильтры «К заказу», «Высокий риск», «Нужны данные». В таблице показаны SKU, товар, текущий остаток, товар в пути, прогноз за срок поставки, заказ, срочность и статус. `—` означает неизвестное значение, а `0` — рассчитанный нулевой заказ.

Откройте `Systeme Electric / 300200851_`: при учебном остатке 9 и нуле в пути рекомендация равна 5. В карточке можно ввести новые датированные значения остатка и товара в пути. Сервер повторно выполняет этапы 5–6; браузер не рассчитывает количество самостоятельно. Нажмите «Как получен результат», чтобы открыть полную страницу этапа 7. Значения, введённые в браузере, хранятся только в памяти текущего запуска API, не меняют Excel и файлы `.analysis/`; после перезапуска вернётся исходный сценарий. Остатки не сверяются автоматически со складом, заказ остаётся черновой рекомендацией.

`pnpm check` запускает lint, проверку типов, тесты и production-сборку; `python -m unittest discover -s backend -p 'test_*.py' -q` проверяет расчёт и API.

## Прежний контракт и синтетический UI

Откройте [http://127.0.0.1:5176/demo](http://127.0.0.1:5176/demo), чтобы пройти прежний сценарий по `contracts/planning-result.schema.json` v0.1.0. Если `VITE_API_BASE_URL` не задан, он использует синтетические данные `src/demo/result.ts` и хранит демо-черновик в `localStorage`. Если указан совместимый сервер, `src/lib/planningClient.ts` вызывает `POST /api/planning-runs`, `PATCH /api/planning-runs/{run_id}/recommendations/{sku}`, `POST /api/planning-runs/{run_id}/approve` и `GET /api/planning-runs/{run_id}/export`. Этот старый контракт не представляет статусы `unavailable` и `provisional` реального pipeline, поэтому новый dashboard использует отдельный адаптер `/api/dashboard` без изменения общего контракта.
